# Atlas release workflow review

Baseline assessed against repository `rishadamin001/research-tracker-app`, main `299dff73576368f2e07c2bba166abbcb9c8d2009`. The public website remains the deployment of `13da2d482e92199432ded947f7c413189b6c222c` from Pages run `43029782654` unless the deployment record changes. The main commit only added documentation and a production verification report after that deployment.

| Control | Baseline | Staged implementation or owner work |
| --- | --- | --- |
| Explicit production release | `workflow_dispatch` and a main-branch check already existed. | Keep manual dispatch and allow an explicitly approved release merge whose commit title starts with `Publish approved Research Atlas `. Check the exact repository and branch on both paths. The run title includes its immutable source SHA. |
| Full check gate | The publishing job ran type checking, unit tests and the build independently of broader CI. | Run the same reusable check workflow from the same commit. Its final step uploads the static build from that revision to Pages. A failed audit, check, build, production policy verification, DOCX inspection or browser test prevents artifact upload and deployment. |
| Least privilege | Package installation, build and publish shared Pages and OIDC write access. Checkout retained its token by default. | The check and build job has `contents: read` and discards checkout credentials. The separate publish job has `pages: write` and `id-token: write`, and only calls the pinned official deploy action. |
| Workflow dependencies | All four Atlas workflows used mutable major tags. | Direct action calls use full official commit SHAs. Pages artifact action v4 also pins its nested artifact action. Keep reviewing and updating pins as vendors publish security patches. |
| Package advisories | `npm ci` did not set an explicit advisory threshold. | Run the npm locked-tree audit including development dependencies with a high-severity failure threshold. npm still prints advisories below that threshold. |
| Live literature dependencies | Existing independent diagnostics can fail for upstream reasons. | Preserve the independent live provider diagnostics and their failure results. Full deterministic browser checks still gate release. |
| Main branch protection | The branch API returned `protected: false`, `protection.enabled: false`, and zero required status checks. | Owner should configure a rule requiring pull requests and the unique `Verify Research Atlas` job, preventing force pushes and branch deletion. Require reviewer approval if an eligible reviewer is available. Confirm the PR check succeeds before making it required. The prepared workflow runs on every pull request targeting main so a root-only or legacy change can satisfy the branch rule. |
| Account and repository settings | The connector could not establish environment approvals, account MFA, Dependabot, secret alert or push-protection settings. | Owner should confirm MFA, admin/collaborator access, dependency alerts, secret scanning alerts and push protection. GitHub's built-in scanning is available for public repositories. Keep enforcement scoped to supported credentials and review signing files independently. Confirm that only main can deploy to the `github-pages` environment and set reviewer approval if suitable. |

The staged files do not apply owner-only settings. Validate the draft PR’s normal checks before considering a merge. After the owner approves a future release, confirm the workflow run displays the reviewed SHA and that the `verify` job succeeds before the publish job starts. The existing Pages configuration already uses GitHub Actions. Atlas uses relative Vite paths and does not consume the `configure-pages` metadata outputs.

Verification of staged YAML passed with actionlint 1.7.12, after SHA-256 comparison against its official release checksums. Local structure checks also confirmed workflow permission boundaries, explicit release entry points, exact checkout, required check commands and upload after all checks. The production build embeds its version and the CI commit in HTML. The published smoke report records these served values separately from the smoke runner's commit, and the manual verification workflow accepts the expected deployed SHA to validate release identity.
