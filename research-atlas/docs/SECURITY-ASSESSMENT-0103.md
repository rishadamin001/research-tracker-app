# Research Atlas 0.10.3 security assessment

Scope is the static web app, browser storage, network calls, imports and release process. Baseline is the published 0.10.2 application at `13da2d482e92199432ded947f7c413189b6c222c`. The project settings observation used main at `299dff73576368f2e07c2bba166abbcb9c8d2009`. The review used source inspection, the lockfile advisory audit, and a real HTTPS response. It does not establish a security certification or test the future Android package. [OWASP ASVS](https://owasp.org/www-project-application-security-verification-standard/) · [OWASP MASVS](https://mas.owasp.org/MASVS/)

## Findings and controls

| Priority | Evidence and effect | Phase 1 disposition |
| --- | --- | --- |
| High, release administration | GitHub reported the main branch as unprotected. Compromise of a write-capable identity can change code that later opens users’ local workspaces. The Pages workflow gave the build job Pages and OIDC permissions and exercised only part of the verification suite. | The proposed workflow pins the actions, checks out the dispatched SHA without retaining Git credentials, requires checks before uploading the same build, and grants deploy permissions only to a separate job. Branch protection, stronger authentication, and environment settings need owner verification. |
| High for confidential research, device and copy access | IndexedDB, snapshots and ordinary exports are readable by someone with access to the browser profile or files. HTTPS and backup checksums serve different purposes. | Keep the existing format and disclosures. A separate encrypted backup design covers the next phase. Review active workspace encryption and key lifecycle before changing its data format. |
| Medium, browser defense | The live app returned no CSP, referrer, `nosniff`, frame or permissions header. An `_headers` file at an application path did not establish live header enforcement. | The production build carries a CSP that restricts script, styles, network connections and workers, plus a referrer policy. Zod uses its non-JIT validation mode so the policy can disallow dynamic scripts. The build also emits `_headers` for supporting hosts, including HTTP-only frame protection. Proof on a future host requires checking its actual responses. |
| Medium, dependency chain | `npm audit` reported seven moderate findings in the development ESLint chain through `minimatch`, and zero high or critical findings. `npm audit --omit=dev` reported zero advisories. | The workflow reports dependency advisories and gates high/critical findings. Do not use untrusted glob configuration. Follow the compatible upstream fix and reassess it separately. [Advisory](https://github.com/advisories/GHSA-g3hv-75wg-m249) |
| Low, bounded validation | A size-bounded backup could still include deeply nested unknown data in the original checksum input. | Checksum traversal now rejects excessive depth with a clear message. Validation still precedes import preview and any storage write. |

Untrusted import text is rendered by React as text. Existing tests cover URL scheme validation, DOI handling, CSV formula neutralization, reference parsing, backup limits and corruption. File imports have explicit size bounds and previews. The Web API endpoints are HTTPS and selected by provider. Search terms and metadata identifiers are sent to the requested service. Third-party sites and exported scholarly documents are separate trust boundaries. The app has no project-upload endpoint or student account.

Existing IndexedDB transaction revision checks protect stale-tab writes. The UI distinguishes confirmed saves from a failed save and offers a recovery download. Browser storage can still fail, get cleared, or become inaccessible, and a device-local snapshot cannot recover a lost device. The service worker caches versioned same-origin assets and keeps the shell for offline use after fetching its assets. A compromise of authorized same-origin code could still reach workspace data, so pinning Actions and controlling repository and hosting access remain necessary.

## Live HTTP observation

The public GitHub Pages app returned HTTP 200 with `Content-Type: text/html; charset=utf-8`, `Cache-Control: max-age=600` and `Strict-Transport-Security: max-age=31556952`. The response omitted `Content-Security-Policy`, `Referrer-Policy`, `X-Content-Type-Options`, `X-Frame-Options` and `Permissions-Policy` on 16 November 2026 UTC. These are observations of the published baseline, not claims about the candidate. The meta policy applies to the HTML document. `frame-ancestors` requires an HTTP response header, as do `nosniff`, HSTS and Permissions Policy. [CSP delivery rules](https://www.w3.org/TR/CSP3/#meta-element) · [Cloudflare Pages headers](https://developers.cloudflare.com/pages/configuration/headers/)

## Owner checks before broader distribution

Require the app CI check on main, review who can merge or run the release, and verify the Pages environment accepts only the intended branch. Enable and confirm GitHub secret scanning and push protection. Keep MFA and account recovery current for GitHub and Google. Keep any signing keys in owner-controlled secure storage. Never include private keys, tokens or passwords in `VITE_` environment variables, app assets or Git history. No repository administration settings were changed during this review. [GitHub Actions security](https://docs.github.com/en/actions/security-for-github-actions/security-guides/security-hardening-for-github-actions)

Before Android distribution, test the final origin and Android package on physical devices and have a reviewer check storage, network behavior and recovery against the actual build.
