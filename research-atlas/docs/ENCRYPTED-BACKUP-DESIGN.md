# Encrypted portable backups

Design for Phase 2. The 0.10.2 app exports plaintext backups and keeps its active workspace in IndexedDB. This document specifies an encrypted export and recovery flow for a subsequent release.

## Storage and compatibility

`src/lib/backup.ts` exports format v3 with a checksum and reads v1, v2 and v3. `src/lib/storage.ts` reads workspace envelopes 1–4 and writes envelope 4. These are independent formats. Keep the plaintext import and export paths, including legacy v1’s unchecked label. The checksum detects accidental changes. Encrypted exports add authentication and confidentiality to the same validated v3 backup payload. Restoring projects uses the current project schema and existing import-as-copies behavior. New copies get new project IDs and a title suffix while preserving established internal references and recorded work. Display preferences are included for reference. Standalone search history, browser cache, tab-local settings, revision counters and snapshots are separate from portable project backups.

The portable copy represents the project state in the current tab at the moment export starts. Finish or cancel any open notebook or evidence editor before exporting to include those changes. Committed questions, question drafts, screening decisions and events, evidence and locators, notebook entries, writing and citation links, and project search records travel in the file. Preserve recognized fields through the same v3 validator. Keep the raw recovery download for unreadable stored data distinct from the validated project backup.

## Proposed file format

Use a binary `.atlas-backup` download with MIME `application/octet-stream`. Read the format bytes rather than trusting the extension or browser-supplied MIME. A compact binary header avoids base64 overhead and allows a cheap size and version check before cryptographic work. Verify the Android picker can select this extension before relying on it in the TWA.

| Byte offsets | Meaning |
| --- | --- |
| 0–7 | ASCII `RAENC001` designates the file type, version and fixed algorithm suite |
| 8–23 | Fresh 16-byte random salt |
| 24–35 | Fresh 12-byte random AES-GCM nonce |
| 36–end | AES-GCM ciphertext followed by its 16-byte tag |

Encode the complete validated v3 backup JSON as UTF-8, within the existing 10,000,000-byte limit. Reject an encrypted file of 52 bytes or fewer, larger than 10,000,052 bytes, or of an unsupported version. Check `File.size` and a bounded header slice before reading the rest of the file. Check the buffer length again at the crypto API boundary. Use the exact 36 header bytes as AES-GCM additional authenticated data. Project names, source origins and record counts live inside the ciphertext. The outer format, file size and filesystem timestamps remain visible. [Web Cryptography Level 2](https://www.w3.org/TR/webcrypto-2/#aes-gcm)

Use secure-context Web Crypto. Derive one non-extractable 256-bit AES-GCM key per export from the passphrase through PBKDF2-HMAC-SHA-256 at 600,000 fixed iterations. Import the passphrase bytes as a non-extractable PBKDF2 key with only `deriveKey` usage, and give the derived AES key only the operation required for that invocation. Use `crypto.getRandomValues()` independently for the salt and nonce on every export, including retries. Request a 128-bit tag. Accept only the fixed suite. Future algorithms and work factors require a new version with dedicated bounds. This design uses established primitives and a per-file key without adding a cryptography package. Benchmark the selected cost on representative Android devices before distribution. [NIST SP 800-132](https://csrc.nist.gov/pubs/sp/800/132/final) · [NIST SP 800-38D](https://csrc.nist.gov/pubs/sp/800/38/d/final) · [OWASP PBKDF2 guidance](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html#pbkdf2)

Use NFC normalization followed by UTF-8 for the passphrase. Preserve spaces and case. Reject malformed Unicode input and cap encoded input at 1,024 bytes before deriving a key. Confirm the passphrase at creation, recommend a long unique passphrase generated by a password manager, and explain that the file can be guessed offline if the passphrase is weak. There is no reset or recovery key. Keep the passphrase separately from the file. Do not persist or log password text, plaintext, or keys. Hold passphrases in the modal or current operation only, clear fields promptly, clear temporary byte arrays where practicable, and drop references in cleanup. JavaScript strings and Web Crypto internals do not offer guaranteed memory erasure.

## User flow and failure handling

- Keep `Download backup` available for the existing plaintext export with a clear plaintext label. Add a distinct `Download encrypted backup` action. If crypto is unavailable or encryption fails, show the error and retain the projects. Require a separate user action for any plaintext export. The last backup timestamp marks a download request, not a successful file write or a verified recovery.
- On selecting an encrypted file, show the passphrase prompt. Return a single authentication error for a wrong passphrase, altered ciphertext, or altered supported header. After authentication succeeds, decode UTF-8 strictly and validate the inner v3 schema, checksum, project count and identifiers with the existing parser. Treat authenticated data as untrusted application input for rendering, links and later exports.
- Offer `Verify backup` for a non-destructive recovery check. Report format, dates and record counts only after decrypting and validating. Drop parsed projects after a verify-only operation. Verify performs no IndexedDB writes, preference updates, snapshot changes, or project selection. Import also uses the validated preview and adds copies only after an explicit confirm action. Recheck current capacity and save eligibility. Let the existing transaction and revision guard protect other tabs. Distinguish copied-in-tab state from a confirmed save and keep recovery export reachable on a write failure.
- Run one operation at a time. Use a request token to discard late results after a new file is chosen, cancellation, navigation, or unmount. Crypto promises can finish after cancellation. Ignore their output and release references. Clear prior preview data when beginning another operation. Disable confirmation until the current result is ready. Leave open drafts, projects and persisted state intact on cancellation, failures and quota errors.

## Verification before release

- **Crypto and parsing.** Test successful decryption against an independently generated fixture for the specified bytes and KDF. Test Unicode passphrases and spaces, wrong passphrase, changes to salt, nonce, version, ciphertext and tag, truncation, appended bytes, invalid authenticated inner data, repeated IDs, extra fields, and exact byte bounds. Verify two exports from the same input use independently generated salts and nonces. Assert oversized or unknown files are rejected before the KDF runs.
- **Compatibility and recovery.** Keep v1/v2/v3 import tests. Export a populated project with committed and draft questions, sources, screening history, notebook entries, located evidence and linked manuscript citations. Verify across fresh browser processes and compare restored data, allowing only documented new IDs and title suffixes. Include near-limit payloads, separate-origin testing, a quota failure and a conflicting tab. Check that verify-only and failed restores do not write to the workspace and that original projects survive a successful import.
- **Browser and device flow.** Exercise chooser, keyboard focus, status, cancellation while encryption/decryption is pending, starting a second operation, reload, and no passphrase retention. Check download and reopen offline on supported browsers. Measure near-limit memory and time in desktop browsers and on physical Android, including file-picker behavior and returning from background. Record the exact release revision and confirmed behavior.

## Active workspace encryption decision

Ship portable encryption first. Active projects and recovery snapshots still reside in normal browser storage. HTTPS protects transport, and OS device encryption is a separate layer. The encrypted file cannot protect an unlocked page, a compromised script or extension, plaintext exports, or data already copied out of the app. Preserve the browser-origin migration flow by importing a verified copy at the destination while the old workspace remains available.

If active encryption becomes necessary, use a separately versioned storage migration and evaluate a random data key wrapped by a passphrase-derived key. Unlock each session explicitly and hold the key only in memory. Prototype how to lock while autosave is pending, preserve revision comparisons across tabs, encrypt snapshots and recovery data, and prevent old clients from writing an encrypted workspace. Check offline unlock and regenerate verification fixtures before considering any switchover. An interrupted migration must leave the prior workspace and a known-good portable backup accessible. Unlocked data remains available to code running in the same origin. A TWA normally uses the browser’s origin and storage model. A native wrapper needs its own storage and migration design if it adds a device-backed key. Test physical devices and larger workspaces before committing to either approach. Lost passphrases require a separately saved recoverable copy under either architecture.
